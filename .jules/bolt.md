## 2024-05-28 - Thread-Safe TTL Caching with Double-Checked Locking
**Learning:** When implementing in-memory TTL caches for endpoints like leaderboards in Python (which has the GIL, but still needs thread-safety for concurrent HTTP requests in Flask/Gunicorn), using a simple lock can cause contention if the critical section is too large. Furthermore, simple checking then locking can cause a "cache stampede" where multiple threads miss the cache simultaneously, wait on the lock, and then *all* perform the expensive operation sequentially once they get the lock.
**Action:** Use the "double-checked locking" pattern. First, check if the cache is valid (fast path, no lock). If invalid, acquire the lock. Inside the lock, check *again* if the cache is still invalid (in case another thread updated it while waiting for the lock). Always recalculate the current time inside the lock for the second check. Finally, minimize the locked block by ONLY updating the cache dictionary and exiting the lock *before* performing expensive operations like `render_template`. Python evaluates `return <expression>` before releasing a `with` block lock, so returning from inside the lock keeps it held during rendering.
